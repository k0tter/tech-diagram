# フローチャート・業務フローの描き方

フロー図を描くときに 1 回 Read する。ワークフロー・meta/legend・--optimize は
SKILL.md と同一。**シーケンス図は引き続き対象外**。

## 図形(nodes.shape。ラベルは箱の中・寸法は自動)

| shape | 意味 | 備考 |
|---|---|---|
| `terminator` | 開始 / 終了 | 濃色塗り。フローの入口と出口に必ず置く |
| `process` | 処理 | 標準の矩形 |
| `decision` | 判断 | ひし形。分岐エッジに必ず `label`(はい/いいえ 等) |
| `io` | 入力 / 出力 | 平行四辺形 |
| `document` | 帳票・書類 | |
| `db` | データストア | 円筒 |
| `subprocess` | 定義済み処理 | 両端に縦線の矩形。`link` に URL / 相対パスを指定すると別図へリンク |
| `gateway` | 並行分岐 / 並行合流(AND) | 「+」入りひし形。fork と join に同じ shape を使う。**無ラベル推奨**(64x64 固定で「+」とラベルが重なる — 補足は流入エッジの label か隣の注記へ。ビルド時 WARN) |
| `delay` | 待機 | 右側が半円の待機記号 |
| `preparation` | 準備 | 六角形 |
| `junction` | 合流点 | 無ラベルまたは1文字の小さい○ |
| `connector` | 連結子 / goto | 参照先を1文字で入れる小さい○ |

```json
{"id": "check", "shape": "decision", "label": "承認?", "col": 1, "row": 2}
```

並行処理(AND)は `gateway`、排他分岐(OR)は `decision` を使い分ける。
fork/join の最小形:

```json
"nodes": [
  {"id": "fork", "shape": "gateway", "col": 1, "row": 0},
  {"id": "work_a", "shape": "process", "label": "処理A", "col": 0, "row": 1},
  {"id": "work_b", "shape": "process", "label": "処理B", "col": 2, "row": 1},
  {"id": "join", "shape": "gateway", "col": 1, "row": 2}
],
"edges": [
  {"id": "e1", "src": "fork", "dst": "work_a", "kind": "main"},
  {"id": "e2", "src": "fork", "dst": "work_b", "kind": "main"},
  {"id": "e3", "src": "work_a", "dst": "join", "kind": "main"},
  {"id": "e4", "src": "work_b", "dst": "join", "kind": "main"}
]
```

別図を開く subprocess は `{"id":"detail","shape":"subprocess","label":"詳細処理","link":"detail-flow.drawio",...}` と書く。

アイコン(AWS 等)や entity と混在してよい(例: 処理の横に対象システムのアイコン)。

## レイアウトの定石(AWS 図と向きが違う)

- **主フローは上→下**: 1 ステップ = row +1。col は分岐とレーンに使う
- 判断の分岐: 本流(はい)は**真下**、例外側(いいえ)は**右か左の col** へ。
  分岐エッジには必ずラベル
- **戻り線(ループ・差し戻し)**: 戻り先の隣接 col を空け、側面回廊を通す。
  ループ継続の「リトライ」等は、本流=真下の例外として上向きに戻してよい
- 開始・終了は同一 col(主フローの col)に置くと一本道が通る
- **再提出**は decision へ直接戻さず、手前の `process` / `io` へ返す。
  decision の4頂点を分岐のために温存できる
- 本流は `main`(実線)、戻り・スキップ・例外脱出は `sub`(破線)で区別する。
  3種以上が必要なら `kinds.style_extra` の `dashPattern` を変える

## 戻りフローの配置原則(レーンをまたぐ差し戻し)

差し戻し・却下がレーンをまたいで戻る図(承認フローの典型)は、素朴に引くと
戻り線が主フローを横断して交差の主因になる。実戦(経費承認 3 レーン)で
効いた順に:

1. **受け側を 1 つに合流させる**: 複数の却下(上長却下・経理却下)は
   それぞれ始点へ戻さず、「申請を修正」のような**単一の修正ステップに合流**
   させてから再提出線を 1 本だけ引く。戻り線の本数が減れば交差も減る
2. **修正ステップは戻り元側の境界寄りに置く**: 戻り先レーン(申請者)の中でも
   **戻り元レーンに近い側の col・上寄りの row** に置くと、戻り線が図を
   斜めに横断しない
3. **戻り線は例外側の線種で**: `sub`(破線)等で本流と区別し、ラベル
   (「却下」「差し戻し」)を必ず付ける — 交差が残っても読み違えない
4. それでも横断が残るなら**戻り専用の空き col を外側に 1 本**確保する
   (回廊として自動配線が使う)。主フロー行を横切る中間 col に
   ノードを足すのは逆効果(SKILL.md 配置原則 2)

## スイムレーン(担当者・部署の帯)

`containers.type: "lane"` を使う。レーン = col の帯(縦レーン)にすると
上→下の時系列と両立して読みやすい:

```json
"containers": [
  {"id": "lane_a", "label": "申請者", "type": "lane"},
  {"id": "lane_b", "label": "上長", "type": "lane"}
],
"nodes": [
  {"id": "start", "shape": "terminator", "label": "開始", "parent": "lane_a", "col": 0, "row": 0},
  {"id": "approve", "shape": "decision", "label": "承認?", "parent": "lane_b", "col": 1, "row": 1}
]
```

- コンテナ=矩形の制約はレーンにも適用される(レーンの col 範囲は重ねられない)
- レーン間の受け渡しは通常の main エッジでよい(レーン境界をまたぐのは正常)

## decision(ひし形)の接続上限

- ひし形の出入りは**頂点 4 つまで**(上=入、左右下=出が基本形)。5 本以上を
  つなぐと同一頂点に矢印が重なる → 排他分岐は2段に分け、並行 fork/join は
  `gateway`、単純な合流点は `junction` を使う
- 既知の非対称: バリデータ W15(上方からの流入は上頂点)の機械検査は
  decision(ひし形)のみで、gateway は対象外(ビルド側の頂点固定は両方に効く)
